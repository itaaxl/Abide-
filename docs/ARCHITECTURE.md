# Architecture

- **Next.js 16 (App Router, TypeScript), Tailwind CSS 4.** All pages render on the server; interactive pieces are small client components. Mutations are Server Actions (POST, with Next.js’s built-in Origin/Host check against cross-site requests). Cache Components is off because almost every page reads preference/auth cookies.
- **Supabase** for PostgreSQL, authentication (email + password with verification, optional Google) and row-level security. `src/proxy.ts` refreshes sessions and sets a per-request CSP nonce.
- **Scripture** comes from `data/bibles/<edition>/` (generated by `scripts/import-bible.ts`) through the `BibleProvider` interface in `src/lib/bible/provider.ts`. Readers request one chapter at a time; the browser never downloads a whole Bible.
- **Anthropic** (server-side only) for Find Guidance.

## Data flow: reading
`/bible/[edition]/[book]/[chapter]` → `getChapter()` reads one JSON file → `Reader` renders paragraphs/poetry from USFM-derived segments. Signed-in users’ bookmarks/highlights/notes for that chapter are loaded with their own session (RLS-filtered).

## Data flow: search
Search builds an inverted index per edition once per server instance (≈38k verses, ~150 ms) and answers each query with posting-list intersections plus prefix expansion; no full scans per keystroke. Matching is accent-insensitive (French) and diacritic-insensitive (Arabic). Highlighting splits the original string into matched/unmatched runs, rendered as React text — no HTML injection, wording unchanged.

## Data flow: guidance
See `src/lib/guidance/pipeline.ts`: crisis check → retrieval (curated topics + corpus search) → Claude chooses among opaque candidate ids with a strict JSON schema → server validates ids, renders verses from the dataset → fallback to curated passages with an honest reason if anything fails.

## Editions and numbering
Book identity uses USFM codes (JHN, 1CO…). Each edition records its own book list, order and verse counts. Cross-edition mapping (`src/lib/bible/mapping.ts`) is conservative: same numbers only when the chapter’s verse count matches; a Psalm-title offset rule; otherwise the app shows the source edition and says why. Saved records always store the edition they were made in.

## Preferences
Stored in the `abide_prefs` cookie (guests and signed-in). On sign-in, saved account preferences replace the device cookie (**account wins at sign-in**); after that, every change writes both, so the latest explicit change wins.

## Timezones
A user’s profile timezone (or, for guests, the browser timezone stored in the preference cookie; default UTC). The daily verse is `rotation[(days since 2026-01-01) mod N]` for the local date. Flashcard due times are absolute instants at local midnight; “due today” means due before the end of the user’s local day, so changing timezone never loses a card.

## Internationalisation
UI strings: `src/lib/i18n/dictionaries.ts` (en/fr/ar for navigation, reader, search, daily verse, footer). `<html lang dir>` follows the UI language; Scripture blocks carry their own `lang`/`dir`, so UI language and Scripture language are independent. Secondary pages (legal, help, admin) are English-only at launch — see CHECKLIST.

## Security summary
- RLS on every private table (owner-only), server-side verified-user checks in every action, admin role not self-assignable (column privileges + `is_admin()` policies).
- CSP with per-request nonce, `frame-ancestors 'none'`, HSTS, nosniff, referrer policy, permissions policy.
- Zod validation for every server input; user text rendered as text only.
- Safe redirects (`src/lib/safe-redirect.ts`) for auth callbacks.
